Accuracy note, since an earlier framing of this got it wrong: the docs do **not**
say `better-sqlite3` requires Node 22. It declares
`engines: node 20.x || 22.x || … || 26.x`, so Node 20 is supported upstream. The
real failure mode is that the native module is compiled against one Node ABI at
install time, so mixing Node majors afterwards breaks it in either direction —
which is what the docs now say, along with the `pnpm rebuild better-sqlite3`
escape hatch.

Limitation worth knowing: on this machine the `engines` guard cannot actually
fire under Node 20, because the corepack `pnpm` shim itself crashes there before
any engine check runs. The field is a guard for environments with a working
pnpm on the wrong Node, not for this one.

**Correction (2026-08-09), after direct testing.** An earlier note here said the
suite "passes zero tests" off Node 22. That was wrong — it was inferred from
`pnpm` failing to start, not measured. Running vitest directly under Node 20
gives **25 of 33 passing, 8 failing**: exactly the `src/history/`,
`src/server.test.ts` tests that open SQLite, with
`NODE_MODULE_VERSION 127 ... requires 115`. The ABI diagnosis itself is
confirmed correct, so CLAUDE.md's wording stands.

Also confirmed: the binding loads **lazily** — `require("better-sqlite3")`
succeeds on any Node version and only throws when a database is opened. A bare
`require` check is not a valid test of ABI compatibility.

Real-world impact found while wiring up the CLI wrappers: in a normal login
shell, Homebrew's `/opt/homebrew/bin/node` (v24.10.0) outranks nvm on PATH, so
`codex-usage usage` was **silently half-failing** — printing usage but losing
history persistence into `history.warning` via `withHistoryPersistence`'s
try/catch. `nvm alias default 22` does not fix this (PATH order beats the nvm
default); the `~/.local/bin` wrappers now pin Node 22 themselves. Worth
considering whether that swallowed-warning path should be louder.

A plan bug found by the executor and worth recording: this plan's Done criteria

The executor flagged the discrepancy instead of "fixing" it by touching `dev` —

### 001 — BLOCKED at Step 0 (2026-08-06, `claude` 2.1.223)

Execution attempted on branch `dev`; the Step 0 go/no-go spike failed, so no
source file was written and no commit was made. The plan's central undocumented
assumption is **false on this version**: a `statusLine` command supplied via
`--settings` does **not** fire during a headless `claude -p` run. The call
exits 0, answers the prompt normally, and spends real quota, but the capture
script is never invoked and no payload is written. This is consistent with
statusLine being a TUI-render feature — headless mode has no status line to
draw.

Independently re-verified by the advisor (zero additional quota spent):

- No `claude usage` / rate-limit subcommand exists on 2.1.223 (`claude --help`
  lists: agents, auth, auto-mode, doctor, gateway, import, install, mcp,
  plugin, project, setup-token, ultrareview, update).
- `~/.claude.json` holds only tier *names* (`userRateLimitTier`,
  `organizationRateLimitTier`) — no percentages, no reset timestamps.
- No file under `~/.claude` contains `used_percentage` or `resets_at`.
  Session transcripts carry per-turn token counts only. (An apparent
  `"rate_limit"` grep hit in `~/.claude/projects/` was this planning session's
  own transcript quoting the plan text — not real data.)

So the plan's claim that there is no free local source stands, and the one
paid path it designed around does not work. **Awaiting a human decision on
direction** — see the options recorded at the end of
`001-claude-usage-limits.md`.

## Key open question this plan surfaces

Plan 001's Step 0 requires a live, one-time manual verification that
Claude Code's `statusLine` hook actually fires in headless (`-p`) mode —
this is undocumented and could not be confirmed from Context7 docs alone
without spending the user's real API quota during the advisor/planning
session (which was avoided on purpose). The plan gives the executor a
concrete command to run once and an explicit STOP condition if it doesn't
work as expected. See "Why this matters" and Step 0 in
`plans/001-claude-usage-limits.md` for full detail, including why the
`@anthropic-ai/claude-agent-sdk` alternative was ruled out (Anthropic's own
docs discourage third-party products from reusing claude.ai login/rate
limits via that SDK without prior approval) — the user was asked and chose
the "spawn the local `claude` CLI directly" approach.
